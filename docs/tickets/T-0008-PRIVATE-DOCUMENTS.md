# T-0008 — Private Documents

Status: `IN_PROGRESS — PARTIALLY_COMPLETE`

## APPROVED IMPLEMENTATION AMENDMENT

The human approval of `T-0008-R2-LARGE-FILE-ARCHITECTURE-REPORT.md` supersedes every older Supabase Storage and 10 MiB statement below. The implemented contract is Cloudflare R2 binary storage, PostgreSQL business metadata, Uppy 6 `signRequest`, a configurable 500 MiB architecture target, 5 MiB multipart threshold, 16 MiB parts, persistent upload sessions, authoritative server-streamed SHA-256, and the `DocumentFinalizationService` runtime boundary. No Supabase Storage bucket or policy belongs to T-0008.

The implementation remains `PARTIALLY_COMPLETE` until a private EU-jurisdiction R2 bucket and its bucket-scoped server credentials are supplied and the mandatory real-R2 gate passes. The 500 MiB value is not an advertised product capability before that gate.

## TITLE

T-0008 — Private Documents

Historical reference: `HUB-008 — Documents privés`. `T-XXXX` remains the only official execution numbering.

## OBJECTIVE

Deliver a secure personal document module for uploading approved file types to a private Supabase bucket, managing minimal metadata, downloading through short-lived signed URLs, replacing files without losing version history, tracking expiration dates, and logically archiving records.

## CONTEXT

T-0003 and T-0007 provide workspace-owned organizations and projects. T-0005 provides missions. T-0008 may attach a document to one optional organization, project, or mission context while keeping the document owned by the personal workspace.

Documents can contain highly sensitive information. Local reports, professional resources, and audit notes are not fixtures and must never be uploaded automatically, copied, parsed, committed, or used in tests. Only synthetic generated bytes and generic metadata are allowed during implementation and verification.

## SCOPE

- Private `professional-documents` storage bucket.
- Document list, creation/upload, detail, metadata modification, replacement/version history, private download, and logical archive.
- Active/archived filters plus organization, project, category, status, and expiration filters.
- Optional organization, project, or mission context with workspace and hierarchy consistency.
- Initial upload allowlist: PDF, PNG, and JPEG only.
- Maximum file size: 10 MiB per version.
- Server-side validation of size, declared MIME type, extension, and recognized file signature.
- Opaque storage paths containing workspace, document, and random version identifiers; original filenames never form storage paths.
- Signed download URL valid for at most 60 seconds and created only after current-workspace authorization.
- Immutable version rows; replacement preserves prior versions and changes the current version atomically at the metadata boundary.
- Expiration states and filters based on `expires_on`; no notification engine.
- Responsive desktop and 360 px mobile flows.
- Loading, error, validation, empty, upload-pending, and unavailable-file states.
- Keyboard navigation, visible focus, accessible names, and automated accessibility checks.
- Unit, DB/RLS, Storage policy, integration, regression, build, and E2E tests.

## DATA_MODEL

### `public.documents`

| Column | Type | Constraints |
| --- | --- | --- |
| `id` | `uuid` | Primary key, generated UUID |
| `workspace_id` | `uuid` | Non-null FK to `workspaces`, cascade on workspace deletion |
| `organization_id` | `uuid` | Nullable same-workspace organization |
| `project_id` | `uuid` | Nullable same-workspace project consistent with organization when both exist |
| `mission_id` | `uuid` | Nullable same-workspace mission consistent with project/organization when supplied |
| `name` | `text` | Trimmed, 1–180 characters |
| `category` | `text` | `identity`, `administrative`, `contract`, `education`, `work`, or `other` |
| `status` | `text` | `draft`, `to_sign`, `submitted`, `valid`, `expired`, or `archived` |
| `issued_on` | `date` | Nullable |
| `expires_on` | `date` | Nullable and not before `issued_on` |
| `notes` | `text` | Nullable, maximum 2000 characters |
| `current_version_number` | `integer` | Positive, starts at 1 |
| `archived_at` | `timestamptz` | Nullable logical archive marker |
| `created_at` | `timestamptz` | Non-null, database-generated |
| `updated_at` | `timestamptz` | Non-null, maintained by trigger |

### `public.document_versions`

| Column | Type | Constraints |
| --- | --- | --- |
| `id` | `uuid` | Primary key, generated UUID |
| `workspace_id` | `uuid` | Non-null workspace boundary |
| `document_id` | `uuid` | Same-workspace FK to `documents`, restrict deletion |
| `version_number` | `integer` | Positive and unique per document |
| `storage_bucket` | `text` | Fixed to `professional-documents` |
| `storage_path` | `text` | Unique opaque path; no original filename |
| `original_file_name` | `text` | Sanitized display metadata, maximum 255 characters |
| `mime_type` | `text` | Allowlisted MIME type only |
| `size_bytes` | `bigint` | Between 1 and 10 MiB |
| `sha256` | `char(64)` | Lowercase hexadecimal checksum |
| `created_at` | `timestamptz` | Non-null, immutable creation timestamp |

Database and storage rules:

- Both tables have composite uniqueness required for workspace-safe foreign keys.
- Context foreign keys reject cross-workspace links; triggers validate organization/project/mission hierarchy consistency.
- At least one version must exist before an uploaded document becomes visible as complete.
- `current_version_number` must reference a version belonging to the same document and workspace.
- Version metadata is immutable after insertion; replacement inserts a new monotonically increasing version.
- The bucket is private and has a 10 MiB server-side file-size limit plus the approved MIME allowlist.
- Storage object paths are exactly `{workspace_id}/{document_id}/{version_uuid}` with a validated optional extension.
- `storage.objects` policies allow authenticated users to select/insert only under their owned workspace prefix and only in the approved bucket.
- No public read policy and no application-level physical delete policy are introduced.
- Document and version tables enable owner-scoped RLS for all database operations; the UI exposes logical archive only.
- Indexes support workspace/archive/status/category/expiration lists and document version ordering.

## ACCEPTANCE_CRITERIA

- Every stored object is private and reachable only through an authenticated, workspace-authorized, short-lived signed URL.
- Anonymous and foreign users cannot list, upload, read, replace, mutate, sign, or delete another workspace’s documents or objects.
- PDF, PNG, and JPEG files at or below 10 MiB are accepted only when MIME, extension, and signature agree.
- All other file types, empty files, oversized files, and malformed signatures are rejected before persistence.
- Storage paths are opaque, non-guessable, workspace-scoped, and contain no original filename.
- Document metadata and optional organization/project/mission links remain hierarchy-consistent.
- Replacement preserves every prior version and checksum while advancing the current version exactly once.
- Upload failure cannot create visible incomplete metadata; metadata failure cleans up only the new orphaned object.
- Expiration dates are validated and documents can be filtered by expiration state.
- Archive is logical and preserves metadata, versions, and linked business records.
- No raw bucket/path value, SQL detail, policy name, or foreign-row existence appears in user errors.
- The complete flow works at 360 px, by keyboard, and without serious accessibility violations.
- No real local document, personal value, secret, or adjacent roadmap feature enters Git.

## SECURITY

- RLS and Storage policies are the authorization boundary; UI filtering is defense in depth.
- Every server operation revalidates authentication and the active workspace.
- The application uses only the signed-in user’s Supabase client; no service-role key is permitted.
- Signed URLs last at most 60 seconds and are generated on demand after document/version authorization.
- File validation does not trust browser MIME or extension alone.
- Original filenames are sanitized for display and never used as paths or response headers without safe encoding.
- Checksums are calculated from uploaded bytes and never accepted from forms.
- No document content, raw bytes, signed URL, secret, or complete filename is written to logs.
- Content disposition uses attachment; inline active-content rendering is not introduced.
- Broader file formats remain blocked until malware scanning is separately designed and approved.

## RISKS

- Sensitive-file exposure: private bucket, complete policies, opaque paths, and short URLs are release blockers.
- MIME spoofing: verify extension, declared MIME, and magic bytes together.
- Orphan objects: define compensating cleanup for partial upload/metadata failures and test it.
- Version races: enforce unique monotonically increasing versions at the database boundary and handle conflicts safely.
- Cross-context corruption: validate composite workspace and organization/project/mission consistency.
- Oversized request memory: enforce limits before buffering where possible and verify the chosen Next.js upload path.
- Scope drift into Contracts/OCR/Search: enforce allowed files and final diff audit.
- Real-data leakage: never use the local reports or professional resource as fixtures.

## ROLLBACK

- Validate schema and Storage policies on disposable local Supabase before review.
- Application rollback removes document routes while leaving private objects and metadata inaccessible but intact.
- Production rollback uses a reviewed forward migration; it never makes the bucket public or automatically deletes objects.
- Failed new uploads may remove only their own newly created orphan object after exact path verification.
- Any RLS, Storage isolation, signed-URL, upload-validation, version-integrity, or real-data failure blocks release.
